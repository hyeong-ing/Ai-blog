# 이미지 조사와 배치

본문·SEO 최종 검토 후 이 정책을 적용한다. 기존 5개 Skill을 유지하며 별도 Skill이나 예약을 추가하지 않는다. 본문·SEO·기존 HTML은 자동 변경하지 않는다.

## 조사

1. 최종 본문과 실제 연결된 fact-check.md를 읽고 어려운 개념·비교·사용 절차 주변에서 2~4개 위치를 검토한다. 필요 없는 이미지는 생략하며 개수를 채우지 않는다.
2. 공식 발표 이미지 → 공식 문서 화면 → 실제 제품 스크린샷 → 직접 만든 비교표·개념도 → 필요한 장식 순으로 검토한다. 해당 주제에 없는 제품 화면을 지어내지 않는다.
3. 외부 후보마다 내용, 원본 페이지·가능하면 이미지 파일 URL, 제공자, 이용 조건 원문 URL과 확인 범위, 블로그 사용 확인 상태, 위치·이유, 캡션, alt를 기록한다. 파일 URL을 못 찾으면 미확인으로 둔다. 공식 자료·모델 라이선스·코드 라이선스가 모든 이미지의 재배포를 허용한다고 추정하지 않는다.
4. 권한 불확실 후보는 `사용자 확인 필요 / 다운로드·재배포 안 함`. 권한이 확인되어도 이번 워크플로는 기본적으로 링크만 제안한다. 파일 확보·화면 캡처는 허용 범위가 명확할 때만 수행하며 실패하면 이유를 남긴다. 출처 표기만으로 사용 허가가 된다고 판단하지 않는다.
5. 개념도는 fact-check에서 채택한 사실만 원본과 다른 구도로 작성한다. 단순 도형·SVG는 코드로 렌더링할 수 있다. 사진이나 실제 UI처럼 위장하지 않고 `설명용 개념도 · 실제 화면 아님`을 표시한다. 새 주장은 fact-check로 돌린다. 생성 도구가 없거나 실패하면 실제 파일 없이 계획만 기록한다.

## 자체 제작 이미지의 기본 디자인

카드형 설명 이미지, 비교표, 구조도, PPT형 다이어그램에는 다음 원칙을 기본 적용한다. 사용자가 별도로 요청하지 않으면 이후 일일 실행에도 유지한다.

- 기본 색상은 흰색·검정·회색만 사용한다. 강조색은 정보 구분에 특별히 필요한 경우에만 이유를 기록하고 사용한다.
- AI 자동 생성물처럼 보이는 장식적 인포그래픽 대신 사람이 편집한 미니멀한 슬라이드·문서 스타일을 지향한다.
- 정보를 우선하고 장식을 최소화한다. 정교한 여백, 일관된 정렬, 제목·소제목·본문의 타이포 위계로 구조를 드러낸다.
- 과한 라운드, 그림자, 장식 아이콘, 패턴, 그라데이션을 사용하지 않는다. 구분이 필요하면 여백과 가는 회색 선을 우선한다.
- 좁은 화면에서도 읽을 수 있는 글자 크기와 충분한 대비를 유지한다. 근거와 실제 화면 여부 표시는 작은 장식 문구처럼 묻히지 않게 둔다.

이 기준은 자체 제작물에 적용한다. 공식 원본 이미지는 디자인을 맞추기 위해 내용을 임의로 바꾸지 않는다. `scripts/prepare-images.mjs`의 기본 개념도도 같은 흑백 편집 스타일을 사용한다.

### 조사에 근거한 제작 규칙

2026-10-17 아래 디자인 시스템·전문기관 원문을 확인하고 프로젝트용으로 적용했다. 목적은 독자의 이해와 편집 완성도다. ‘AI 제작 여부를 알아볼 수 없다’는 보장이나 사람 제작물로 위장하는 표현은 하지 않는다. 설명용 개념도와 실제 화면의 구분은 유지한다.

1. **레이아웃보다 전달할 내용을 먼저 정한다.** 한 이미지가 답할 질문 하나와 핵심 결론 한 문장을 먼저 쓴다. 본문을 그대로 여러 카드에 복사하지 않는다. 그림이 관계·차이·순서를 더 잘 설명하지 못하면 표나 본문으로 대체한다. 중요한 정보는 본문에도 남긴다. [D1, D4]
2. **정보의 관계에 맞게 형식을 고른다.** 같은 기준의 차이는 비교표, 시간 순서는 흐름도, 구성 요소의 연결은 구조도, 독립적인 항목은 목록으로 표현한다. 단순 목록에 화살표를 붙여 인과관계나 순서를 암시하지 않는다. 모든 주제를 동일한 2열 카드로 만들지 않는다. 현재 생성기의 2열 형식에 맞지 않으면 억지로 끼우지 말고 적합한 별도 SVG·표를 제작하거나 한계를 보고한다. 이는 프로젝트의 편집 판단 기준이다.
3. **위계는 세 단계로 제한한다.** 제목·소제목·본문의 크기를 먼저 정하고, 같은 역할에는 같은 스타일을 쓴다. 기본적으로 한 글꼴 계열과 보통·굵게 두 굵기를 사용하며 명령어만 고정폭 글꼴을 허용한다. 보조 정보는 배치·여백으로 구분하고, 새 글자 크기를 계속 추가하지 않는다. NN/G는 2~3개 크기로 위계를 만드는 방식을 권고한다. [D1, D3]
4. **공통 정렬선을 만든다.** 한글 설명과 제목은 왼쪽 정렬을 기본으로 한다. 표의 숫자는 오른쪽, 비교 항목은 같은 행에 맞춘다. 중앙 정렬은 짧은 노드명 등 필요한 경우만 사용한다. 문장 길이를 맞추려고 사실이나 의미를 바꾸지 않는다. 좌우 대칭 자체를 목표로 하지 않고 정보의 무게를 살핀다. [D1, D3 및 프로젝트 적용]
5. **여백을 체계적으로 배분한다.** 관련 항목 사이보다 다른 그룹 사이를 더 넓게 둔다. 8px 계열의 간격을 기본 단위로 삼되 글자의 시각적 정렬은 소폭 보정할 수 있다. 1200px 폭 제작물의 시작값은 바깥 여백 64~80px, 열 간격 64~80px, 항목 간격 24~32px, 그룹 간격 48~64px다. 여백을 채우려고 장식이나 문장을 추가하지 않는다. 8px 체계는 Atlassian의 접근을 참고했고, 이 수치는 프로젝트 기본값이며 보편 규격이 아니다. [D1, D2]
6. **문구를 먼저 편집하고 글자를 줄이지 않는다.** 짧고 구체적인 제목과 병렬적인 항목명을 쓰고, 반복 라벨·막연한 홍보 문구를 지운다. 한글은 단어·의미 단위로 줄바꿈한다. 긴 URL·상세 출처·긴 주석은 이미지 캡션이나 가이드로 옮긴다. 필수 제한 조건은 삭제하지 않는다. 텍스트가 많으면 내용을 나누거나 표·본문으로 돌린다. [D3, D4 및 프로젝트 적용]
7. **도형은 의미가 있을 때만 쓴다.** 그룹은 우선 여백으로 구분하고 필요할 때만 얇은 선을 사용한다. 모든 문장을 상자로 둘러싸지 않는다. 화살표는 방향·의존 관계를 설명할 때만 쓰고 교차를 줄인다. 장식용 번호·이모지·아이콘·영문 배지·과장된 큰 숫자를 반복하지 않는다. 기존 흑백·무장식 원칙을 유지한다. [D1, D4 및 사용자 선호 적용]
8. **비교는 동일한 기준으로 한다.** 양쪽에 같은 속성·단위·기준 시점을 사용한다. 확인하지 않은 빈칸은 미확인으로 표시한다. 면적·굵기·배치가 검증하지 않은 성능 우열을 암시하지 않게 한다. 표의 숫자 정밀도와 단위를 통일하고 불필요한 셀 테두리를 줄인다. 이는 사실 검증 정책과 함께 적용하는 프로젝트 편집 기준이다.
9. **축소된 실제 크기에서 읽는다.** 원본 확대 화면만 보지 않고 블로그 표시 폭과 모바일 약 390px 폭에서도 확인한다. 1200px 원본에서 작은 주석을 추가하는 대신 핵심 문구를 줄이고, 모바일에서 못 읽으면 세로형·분할 이미지를 별도 검토한다. 일반 텍스트와 이미지 속 텍스트의 명암비는 4.5:1 이상을 기본 목표로 한다. 큰 텍스트의 3:1 예외는 실제 표시 크기를 판단한 경우만 적용한다. 이것만으로 WCAG 전체 준수를 주장하지 않는다. [D4, D5]
10. **출력 후 편집 검수를 한다.** 실제 PNG·SVG를 열어 글자 잘림, 줄바꿈, 글꼴 대체, 정렬선, 표의 기준 일치, 불필요한 반복을 확인한다. 이미지 가이드에 전달 목적·형식 선택 이유·표시 크기 검토 결과·미해결 사항을 간단히 기록한다. 검토하지 않은 항목을 완료로 표시하지 않는다. 기존 고정 템플릿으로 렌더링했다는 사실만으로 이 규칙을 통과한 것으로 간주하지 않는다.

### 제작 전후 확인표

- [ ] 이 이미지가 설명하는 질문과 핵심 메시지가 하나로 명확한가?

- [ ] 같은 역할의 글자·간격·정렬이 일관적인가?
- [ ] 관련 항목이 가까이 묶이고 다른 그룹과 구분되는가?
- [ ] 불필요한 상자·화살표·아이콘·반복 문구를 제거했는가?
- [ ] 비교 기준과 근거가 일치하고 실제 화면 여부를 정확히 표시했는가?
- [ ] 실제 게시 폭과 모바일에서 읽히며 필수 정보가 본문에도 있는가?
- [ ] 실제 출력물을 확인했으며 미확인 항목은 가이드에 남겼는가?

### 디자인 근거와 적용 범위

원문은 일반 UX·서비스 디자인 기준이다. 블로그 설명 이미지에 적용하는 세부 편집법과 수치는 이 프로젝트의 해석이며, 특정 스타일이 더 자연스럽다고 실증된 결과로 소개하지 않는다. 출처의 브랜드 글꼴·색상·이미지를 복제하거나 다운로드하지 않는다.

- **D1 — [NN/G: 5 Principles of Visual Design](https://www.nngroup.com/articles/principles-visual-design/)**: 크기와 위계, 균형, 대비, 근접성으로 정보를 조직한다. 2~3개 글자 크기를 권고하며 균형이 반드시 대칭을 뜻하지는 않는다. 프로젝트에서는 흑백의 명도·크기·간격으로 적용한다.
- **D2 — [Atlassian: Spacing](https://atlassian.design/foundations/spacing/)**: 8px 기반의 제한된 간격 체계로 일관성을 만든다. 프로젝트의 이미지 여백 수치는 이를 참고한 자체 기본값이다.
- **D3 — [Atlassian: Typography](https://atlassian.design/foundations/typography)**: 가독성, 시각적 조화, 사용자 맥락을 우선하고 제목·본문·코드의 역할과 행간을 체계화한다. 브랜드 폰트 대신 사용 가능한 한국어 시스템 글꼴로 적용한다.
- **D4 — [GOV.UK: Images](https://design-system.service.gov.uk/styles/images/)**: 불필요한 장식 이미지를 피하고 이미지가 없어도 정보가 전달되게 한다. 텍스트를 이미지로 만드는 방식을 피하라는 권고에 따라 비교 데이터는 가능한 실제 표로, 긴 설명은 본문으로 제공한다. 개념도는 시각적 보조로만 쓴다.
- **D5 — [W3C: Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)**: 텍스트와 이미지 속 텍스트의 최소 명암비는 일반적으로 4.5:1, 큰 텍스트는 3:1이다. 축소 표시를 고려해 프로젝트는 4.5:1을 기본 목표로 삼는다.

## 검색·접근성 기준

2026-10-17 아래 공식 원문 확인. 매 실행에서 최신 원문 접근 상태를 기록하며 검색 순위·AI 인용·색인을 보장하지 않는다.

- [Google 이미지 SEO](https://developers.google.com/search/docs/appearance/google-images): 관련 설명 가까이 배치하고 구체적인 파일명·캡션·자연스러운 alt를 쓴다. 게시 플랫폼에서는 img의 src로 접근 가능한 파일을 연결하고 폭·높이·반응형 표시와 크기를 확인한다. 로컬 파일 생성만으로 검색 수집이 적용되지는 않는다.
- [네이버 콘텐츠 작성](https://searchadvisor.naver.com/guide/content-basic): 중요한 정보는 본문 텍스트로도 제공하고 alt에는 꼭 필요한 설명을 쓴다.
- [네이버 사이트 최적화](https://searchadvisor.naver.com/guide/report-seo): alt에 상위 노출을 위한 동일 문구를 반복하지 않는다.

서비스별 규칙을 혼동하지 않는다. 이미지에만 새 정보를 담지 않는다. 장식 이미지라면 게시 시 빈 alt를 검토한다. 개념도의 글씨는 축소해도 읽을 수 있게 만들고 긴 설명은 본문에 둔다. SVG를 지원하지 않는 플랫폼은 PNG로 변환 후 확인하며 이미지용 구조화 데이터·라이선스 메타데이터는 실제 권한을 확인한 경우만 제안한다.

## 산출물과 실행

`research_dir/image-plan.json`에 다음 계약으로 조사 결과를 저장한다. 이는 웹 조사를 마친 에이전트가 채우는 입력이며 스크립트가 권리나 사실을 자동 인증하지 않는다.

- `checkedOn`, `body`(프로젝트 상대 경로), `researchDir`, `summary`, `errors` 배열
- `candidates` 배열의 항목: `id`, `type`(external 또는 concept), `content`, `sourceUrl`, `imageUrl`(미확인이면 빈 문자열), `provider`, `rights`, `rightsUrl`, `useStatus`, `position`(정확한 본문 소제목 포함), `reason`, `caption`, `alt`, `decision`, `evidence`(검증 ID/원문 근거)
- concept 중 실행할 항목에는 `diagram`: `title`, `root`, `leftTitle`, `leftLines`(최대 3개), `rightTitle`, `rightLines`(최대 3개), `footer`. 각 글줄은 24자 이하. `evidence`에 채택 사실을 연결한다.

`node scripts/prepare-images.mjs research/YYYY-MM-DD/topic/image-plan.json`을 실행하면 실제 생성된 SVG를 `posts/assets/<본문 stem>/`에, 가이드를 `posts/drafts/<본문 stem>-image-guide.md`에 저장한다. 같은 파일은 덮어쓰지 않고 새 버전으로 저장한다. 이 도구는 외부 파일을 다운로드하지 않고 SVG 텍스트를 이스케이프한다. PNG가 필요하면 사용 가능한 로컬 렌더러로 변환하고 실제 생성 여부를 가이드에 덧붙인다.

### 사용자에게 전달하는 본문의 이미지 자리 표시

앞으로 새 초안·예시 본문을 작성해 전달할 때는 채택한 이미지의 삽입 위치에 독립된 한 줄로 `(설명용 개념도 이미지 첨부)`와 같은 안내 문구를 넣는다. 형식은 `({이미지 이름} 이미지 첨부)`이며, 실제 이미지 이름을 사용하고 중첩 괄호나 바깥쪽 ‘이미지 … 첨부’ 문구를 덧붙이지 않는다. 예: `(기존 방식과 변경된 방식 비교표 이미지 첨부)`. 이는 사용자가 문구를 지우고 직접 이미지를 첨부하기 위한 편집용 자리 표시다.

채팅에서 본문 전체를 보여줄 때도 같은 위치에 같은 문구를 유지한다. 이미지가 필요 없어 생략한 위치에는 표시하지 않는다. 확보·권한이 미확인인 후보를 채택된 이미지처럼 표시하지 않는다. 실제 생성 여부와 파일·권한 상태는 별도 이미지 가이드에서 정확히 보고한다.

이 요청은 앞으로 작성할 초안의 자리 표시를 허용한다. 기존 본문을 소급 변경하거나 실제 이미지를 자동 삽입하는 허용은 아니다. SEO 파일에는 자리 표시를 넣지 않는다. 이미지 계획을 마친 뒤 새 본문의 자리 표시까지 확정하고, 해당 Markdown으로 HTML 미리보기를 최종 생성하거나 갱신한다. 변환 시 문구를 누락하지 않는다.

실제 이미지는 자동 삽입하지 않고 가이드의 위치·캡션·alt와 함께 전달한다. 현재 HTML 변환기는 이미지 로딩을 차단하므로 자리 표시만 있는 미리보기에 이미지가 배치됐다고 보고하지 않는다. 기존 원문 수정·실제 이미지 삽입은 별도 요청으로 진행한다.

이미지 조사·권한·다운로드·캡처·렌더링·가이드 저장 오류를 구분한다. 오류는 가이드 또는 research_dir/image-status.md와 최종 응답에 기록하고 본문·SEO·일반 HTML 생성을 계속한다. 파일 저장도 불가능하면 최종 응답에 남긴다. 불확실한 이미지를 대체하는 가짜 UI를 만들지 않는다.
