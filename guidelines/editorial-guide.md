## 여덟 가지 편집 결정

1. 제목: 정확한 제품명 + 변화/독자의 질문. 버전이 논점일 때만 포함한다. “개발 끝”, “무조건 써야 할” 등 결론을 과장하지 않는다.
2. 첫 문단: 날짜·무슨 변화·누가 무엇을 할 수 있는지 먼저 쓴다. 배경의 긴 역사는 뒤로 보낸다.
3. 정보 순서: 핵심 요약 → 이전과 차이 → 활용 → 조건·한계 → 관찰할 점. 독자에게 불필요한 절은 삭제한다.
4. 용어: 처음 나올 때 한 문장으로 풀이한다. 예: MCP는 AI 도구와 외부 데이터·기능을 연결하는 프로토콜이다. 약어를 반복 설명하지 않는다.
5. 예제: 공식 문서로 확인한 명령·코드만 버전과 조건을 붙여 제공한다. 설계 아이디어는 “활용 아이디어”로 표시하고 성공 사례처럼 쓰지 않는다.
6. 표·이미지: 같은 기준으로 비교할 항목이 있을 때 표를 쓴다. 그림이 없어도 이해되도록 핵심은 텍스트로 남긴다. 그림을 만들지 않았으면 alt나 캡션을 꾸며내지 않는다.
7. 출처: 사실 문장에 직접 링크, 마지막에 주요 자료 목록. 사용자 의견은 발언자를 한정하고 공식 사실과 별도 문단으로 쓴다.
8. 읽기 흐름: 한 문단에 한 논점, 의미 있는 H2/H3, 짧고 자연스러운 문장. 요약·도입·결론이 같은 말을 반복하면 줄인다.

## 주제별 구성

- 뉴스/업데이트: 발표와 실제 제공을 구분 → Before/After → 개발자 활용 → 비용·권한·제한.
- Skill: 해결하는 작업 → 기존 처리 → 지침이 바꾸는 부분 → 입력·결과물·연결 → 적용 조건. 설치 경로는 해당 도구 공식 문서로 확인.
- Tool: 대상 사용자 → 가능한 작업 → 접근 방법 → 대안과 구체적 차이 → 비용·환경·제한.
- Workflow: 기존 병목 → 역할·단계·산출물 → 사람이 판단할 지점 → 적용 범위와 실패 조건.

## 한국어 문장과 경험 구분

공식 자료를 읽은 글은 “공식 문서에 따르면”, 회사 성능 수치는 “회사가 보고한 수치”로 쓴다. 해석은 “이 사례에서 참고할 점은”, 활용은 “이런 작업에 적용을 검토할 수 있다”처럼 범위를 드러낸다.

직접 테스트 기록이 없으면 “직접 써보니”, “테스트 결과”, “확실히 체감된다”를 쓰지 않는다. “혁신적”, “게임 체인저”, “압도적”, “완전히 바꿨다” 같은 근거 없는 수식어와 “빠르게 변화하는 시대에” 같은 상투적 도입을 피한다. 번역투·불필요한 영어 병기·중복 결론을 줄인다.

최종 본문에는 작업 상태표·검증 ID·빈 템플릿을 노출하지 않는다. 조사 상태와 편집 메모는 조사 파일과 SEO 파일에 둔다. 문서 조사 기반이라는 설명과 독자에게 필요한 제한은 본문에도 남긴다.
