# 주제 선정 정책

## 목적과 탐색 범주

AI 생태계를 꾸준히 학습하고 기록한다. 트래픽·속보 경쟁이 목적은 아니다. 발표 규모보다 개발자가 새롭게 할 업무, 반복 작업 개선과 현실적 적용 경로를 우선한다.

중요 발표 / 개발자 업데이트 / Skill / Tool / Workflow 다섯 범주를 함께 탐색한다. 범주는 탐색 대상이며 선정 순위가 아니다. Skill과 Workflow를 큰 뉴스가 없는 날의 잔여 후보로 취급하지 않는다. 후보 개수·기업별 전수조사를 채우지 않는다.

## A/B 유형

- A 실전 활용형: 일반 개발자가 접근 경로와 조건을 확인하고 실제 업무에 적용할 수 있는 기능·Skill·Tool·Workflow. 유료도 가능하나 플랜·현실적 비용·환경·권한을 확인한다. 특정 조직 상품 이용자만 가능한 기능은 대상을 한정하고 접근성·일반 관련성에 반영한다.
- B AI 변화 관찰형: 당장 일반 개발자가 쓰기 어렵지만 기술·산업 변화로 기억할 가치가 큰 발표. 대형 인프라·특수 장비 전문가 대상은 명시한다. 자체 호스팅이 중심인 후보를 요금 미확인 API 경로 하나 때문에 A로 바꾸지 않는다. 구체적인 접근 경로를 검증해 글의 초점을 바꾸면 재분류할 수 있다.

일상 선정은 적합한 A를 우선한다. B는 기술·향후 영향의 범위와 근거, 지금 관찰할 가치가 매우 크고 적합한 A보다 먼저 기록할 이유를 구체적으로 설명할 수 있을 때 예외 선정한다. 총점으로 접근 제약을 상쇄하지 않는다. 고정 비율·뉴스 할당량은 없으며 A가 없다는 이유로 부적합한 B를 채우지 않는다.

## 점수 전 사전 적합성 검사

모든 후보마다 다음 다섯 답과 공식 근거·미확인을 기록한다.

1. 누구에게 유용한가? 직무·업무·기존 도구와 수혜 범위를 적는다.
2. 무엇을 새롭게 할 수 있는가? 기존 처리 → 변경 뒤 작업 → 기대 산출물을 적는다. 실측 효과와 활용 제안은 구분한다.
3. 일반 개발자가 현실적으로 접근할 수 있는가? 가입·플랜·단가/과금 방식·OS·장비·지역·권한·제공 상태를 확인한다. 주요 접근 조건이 불명확하면 추가 조사한다.
4. 공식 자료로 구체적인 사용 방법을 설명할 수 있는가? 시작·설정·적용 예제 URL과 직접 테스트 여부를 적는다.
5. 지금 알아둘 이유는 무엇인가? 제공 확대·지원 종료·새 작업 흐름·아직 다루지 않은 현재의 실용성 등을 명시한다. 문서 수정일을 출시일로 쓰지 않는다.

판정: A 적합 / B 관찰 적합 / 추가 조사 / 부적합 / 중복 제외. 1·2·4·5에 구체적인 답이 없거나 핵심 공식 근거가 없으면 우선 선정하지 않는다. 3의 접근 곤란을 확인했다면 B를 검토할 수 있지만 이유를 모르는 상태는 B 통과가 아니다. 유력 미검증 후보는 추가 조사/보류하며 없는 후보로 지우지 않는다. ‘생태계에 도움’, ‘선택지 추가’만으로 통과시키지 않는다.

각 항목에 점수와 구체적 이유를 적고 합계를 확인한다. 이는 편집 판단이며 성능 측정치가 아니다. 근거 부족은 추정과 이유·추가 질문을 남긴다. 주요 접근 조건 불명 후보는 높은 추정 합계로 확정하지 않는다. 비슷한 점수는 정밀한 차이가 아니므로 실제 업무·조건으로 선택 이유를 설명한다. 임의 통과 점수·비율을 추가하지 않는다.

커뮤니티 리뷰는 존재·버전·직접 경험 여부를 보조 맥락으로 조사한다. 점수 항목이 아니며 리뷰 부족만으로 검증된 유용한 기능을 탈락시키지 않는다. 경험을 만들지 않고 본문 리뷰 절은 생략할 수 있다.

## 실행과 작성 전 관문

1. topics/published.md, topics/candidates.md, 기존 초안을 읽고 제품·기능·핵심 변화의 실질 중복을 확인한다. KST 날짜·시각을 기록한다. 지정 주제도 적합성·검증을 생략하지 않는다.
2. 최근 24~48시간의 발표와 실용적인 Skill/Tool/Workflow를 함께 웹 검색한다. 필요하면 최근 7일로 넓히고 evergreen은 현재 유효성을 확인한다. OpenAI·Anthropic·Google/DeepMind·Microsoft/GitHub·Meta·NVIDIA·Hugging Face·Cursor·오픈소스 중 실제 검색·원문 확인 범위만 적는다.
3. 대상 개발자·업무 및 사전 다섯 질문을 확인하고 활용 가능성·접근성을 조사한다.
4. A/B와 적합성 판정 뒤 새 배점으로 평가한다. 추가 조사·부적합·중복의 점수는 참고치일 뿐 선정 자격이 아니다.
5. 적합한 A 중 일반 개발자에게 가장 가치 있는 주제를 고른다. 작은 직접 효용 업데이트가 대형 발표보다 앞설 수 있다. B 예외는 적합 A와 비교해 지금 먼저 기록할 이유를 남긴다.
6. 최종 확정 전에 아래 네 답을 남긴다. 부적합하면 다른 후보를 검토하거나 선정 없음/보류로 종료한다.

- 이 글을 읽은 개발자는 무엇을 얻는가?
- 실제로 사용할 기능이나 적용 방법이 있는가?
- 그 활용 가능성은 공식 자료로 뒷받침되는가?
- 지금 알아둘 이유가 있는가?

A는 적용 경로·조건을 답한다. B는 당장 적용할 방법이 없음을 명시하고 어떤 기술 변화를 어떤 근거로 관찰할지, 실전 도입을 주장하지 않는 범위를 답한다. 기술 중요성을 이유로 없는 활용 사례를 채우지 않는다. 최종 본문 작성 가능 여부는 후속 fact-check가 별도 판정한다.

## 결과·실패·보존

research/YYYY-MM-DD/topic-candidates.md에 정책 버전·실행 시각·기간·검색어·확인 범주, 후보별 URL·발표일·대상·사전 다섯 답·접근 조건·미확인·A/B·적합성·항목별 점수와 근거·추정·중복 판정·선정/보류 이유·최종 네 답·slug·다음 단계를 기록한다.

official-research.md는 source-policy의 주장 ID·원문·날짜·버전·조건·이전 대비 변화·미확인을 따른다. 연구 발표와 실제 이용 가능을 구분한다. 검색 실패·원문 접근 실패·검증 부족·접근 조건 불명·중복·실용성 부족·선정 없음은 구분하고 허위 샘플을 만들지 않는다.

topics/candidates.md는 기존 행을 보존해 상태·새 경로를 추가하며 게시 기록은 사용자 확인 없이 바꾸지 않는다. 같은 날 추가 주제는 research/YYYY-MM-DD/<topic-slug>/를 쓰고 후속 Skill에 동일 research_dir를 전달한다. 재평가는 새 보고서로 저장하고 기존 연구·점수·본문을 덮어쓰지 않는다. 일반 재실행도 기존 파일을 읽고 별도 수정본이나 추가 이력으로 보존한다.
